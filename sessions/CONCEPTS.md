| Concept | Summary | Challenge | Sessions |
|---------|---------|-----------|----------|
| Architecture of an interpreter | Keep logic pure (functional core) and push I/O to the edge (imperative shell). Layers map onto a shell, but parsing is domain, because the language is the product | shell | [001](001-2026-10-14-shell.md) |
| Command lookup and execution in a shell | Builtins first, then PATH in order; a match is a regular file with an execute bit. PATH is user data, so failures mean "try the next entry". bash caches lookups lazily, zsh can fill its table up front. Running uses `execve(path, argv)`: the file to load and `argv[0]` (the short name) are separate, mirrored by `exec.Cmd.Path`/`Args` | shell | [002](002-2026-10-15-shell.md), [003](003-2026-10-15-shell.md) |
| Error handling across boundaries | Adapters translate OS-specific errors into what the core understands, so the core doesn't import `os/exec` or `os`. Tell failure kinds apart (couldn't start vs exited non-zero) with `errors.As` | shell | [003](003-2026-10-15-shell.md) |
| Go's I/O model | `io.Reader`/`io.Writer` are one-method interfaces satisfied implicitly; wrappers like `bufio.Reader` add behaviour, and a buffered reader must live as long as its stream. A process has separate stdout and stderr; pass writers to the code that produces output | shell | [001](001-2026-10-14-shell.md), [003](003-2026-10-15-shell.md) |
| Interfaces and dependency injection in Go | The consumer owns the interface ("accept interfaces, return structs"); implicit satisfaction connects them; `main` is the composition root. Inject a capability, not a snapshot of data; every adapter that talks to the OS (filesystem, processes) gets its own port | shell | [002](002-2026-10-15-shell.md), [003](003-2026-10-15-shell.md) |
| Modelling command results | Output is not part of the result: commands write to the streams they are given, like real processes. The result carries only exit code and "should stop"; the exit status is a separate channel (`os.Exit`, `$?`) | shell | [001](001-2026-10-14-shell.md), [003](003-2026-10-15-shell.md) |
| Package and API design | Name packages after what they provide, avoid stutter, export only what callers need. Deep modules over shallow layers; comma-ok over sentinels when absence is possible. Name related things as one consistent group (`stdin`/`stdout`/`stderr`, `ExecutableFinder`/`ExecutableRunner`) | shell | [002](002-2026-10-15-shell.md), [003](003-2026-10-15-shell.md) |
| Testability as design feedback | Hard-to-test code is design feedback. Inject I/O and dependencies, test through the contract (external `_test` packages), and fake only at boundaries (spy fakes record calls); test the adapters themselves against the real OS. Watch every test fail once, and drop tests that duplicate another | shell | [001](001-2026-10-14-shell.md), [002](002-2026-10-15-shell.md), [003](003-2026-10-15-shell.md) |
| When to refactor | Preparatory refactoring: refactor when a stage fights the design ("make the change easy, then make the easy change"). Extract a package when a stage forces that boundary, not up front | shell | [001](001-2026-10-14-shell.md), [002](002-2026-10-15-shell.md) |
