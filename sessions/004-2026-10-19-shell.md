## Concepts learned
- **Exit status conventions** — 0 success, 1 general failure, 126 found but not executable, 127 not found (POSIX 2.8.2, 2.9.1). Builtins that fail return 1 (bash's `EXECUTION_FAILURE`); 126/127 mean "couldn't run the command at all" (`repl.go`, the `const` block).
- **Naming a group of constants** — a shared prefix (`exit*`) and one `const ( ... )` block so they read like an enum; bash does the same in `shell.h` (`EXECUTION_SUCCESS`, `EX_NOTFOUND`).
- **A value nobody reads is a value nobody tests** — `code: exitCommandNotFound` is set but dropped by `Run`, so a test can't observe it. In bash it surfaces through `$?` and `exit` without arguments.
- **When to inject a dependency** — an interface pays off when the real thing makes tests slow, flaky or hard to set up (PATH lookup, starting processes). `os.Getwd` is fast and deterministic, so no seam yet. `os.Chdir` changes the directory for the whole test process, which is what will force the decision for `cd`. Real bash keeps the directory in both places: `chdir` for child processes and `$PWD` as its own state.
- **Untested behaviour** — the "too many arguments" check could be deleted without any test failing. Either test it or drop it.
- **`Fprintf` vs `Fprintln`** — `Fprintf` for messages with placeholders, `Fprintln` for fixed strings or plain values; `Fprintln` doesn't format, it joins its arguments with spaces and adds `\n`. `go vet` catches both mistakes, and `go test` runs vet first.
- **Commit before you submit** — `codecrafters submit` makes its own commit, which hides what changed.

## Design decisions
- 127 for "command not found" now, tested later — alternative: make the last status observable now (`exit` without args uses it). Left until a stage needs `$?`.
- `pwd` calls `os.Getwd` directly — alternative: a working-directory interface. Revisit with `cd`.
- `pwd` with arguments fails with exit 1 (like zsh) — alternative: ignore the arguments (like bash 3.2).
