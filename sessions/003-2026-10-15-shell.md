## Concepts learned
- **Give the writer, don't return the text** — handlers write to `stdout`/`stderr` instead of returning output; works for builtins and external programs alike, and matches how bash builtins write to fd 1 (`repl.go:18`).
- **stdout vs stderr** — two separate streams; errors go to stderr so `cmd 2>/dev/null` and pipes work. The CodeCrafters tester merges them, so only our own tests can tell them apart.
- **Naming consistency** — `stdin`/`stdout`/`stderr` as one group instead of `input`/`output`/…; `ExecutableRunner` pairs with `ExecutableFinder`.
- **A test you've never seen fail** — a check on the wrong buffer passes whether the code works or not. Break the code on purpose to see the test go red (the idea behind mutation testing).
- **Don't duplicate tests** — dropped a test whose behaviour (`"a\n"`) was already covered.
- **`execve(path, argv)`** — the file to load and `argv[0]` are separate; by convention `argv[0]` is the short name. Go mirrors it with `exec.Cmd.Path` and `exec.Cmd.Args`.
- **`exec.Cmd`: describe, then run** — fill the struct, then `Run()` with no arguments; `exec.Command` does its own PATH lookup, which we don't need (`process.go`).
- **Prepend with `append`** — `append([]string{first}, rest...)`; `...` spreads the slice.
- **Translating errors at the boundary** — `process` turns `*exec.ExitError` into "not an error", so `shell` never imports `os/exec`; same idea as the finder hiding `os.Stat` errors behind a `bool`.
- **`errors.As`** — needs a pointer to a variable of the target type (`var e *T; errors.As(err, &e)`); `errors.As(nil, …)` is false.
- **Spy fake and integration tests** — `fakeRunner` records calls to check what the shell asked for; the real `process.Runner` is tested against real programs (`/bin/sh -c "exit 3"`).

## Design decisions
- Handlers get `stdout`/`stderr` — alternative: keep returning text (can't work for external programs).
- `handlerResult` keeps only `code` and `shouldExit` — alternative: a render func in the result (no job for it once handlers write).
- Fallback handler in `shell` for non-builtins — alternative: special-case it in `Run`.
- Inject `ExecutableRunner` — alternative: call `os/exec` inside `shell` (every test would start real processes).
- Runner gets both path and name — alternative: path only (Arg #0 would be the full path) or name only (a second PATH lookup).
- Separate package `process` with `process.Runner` — same pattern as `pathlookup`.
- Non-zero exit is not an error; only start failures are reported — like bash. The exit code is dropped for now.
